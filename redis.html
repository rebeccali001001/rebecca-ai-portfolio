MODULE 07 · SYSTEM ARCHITECTURE

Redis

A fast in-memory data store commonly used for cache, sessions, rate limits, counters, and temporary state.

01 · What is it?

Redis is a shared data store that keeps commonly needed values in memory so applications can read or update them quickly.

It is often used for data that is fast-changing, short-lived, or expensive to calculate again. Redis can support persistence and replication, but teams usually choose it for speed and simple access patterns—not as an automatic replacement for a durable system of record.

02 · Think of it like...

A labeled tray at a busy service counter

The back room holds the official records, but the staff keep today's most-used tickets in a tray within arm's reach. They can respond immediately, update a small number, or discard an expired ticket.

Redis plays that fast shared-tray role for software. The tray is useful because it is close and quick; it should not silently become the only place an important business record exists.

03 · What does it do?

An application reads from Redis before doing slower work, or writes a small piece of temporary state that several application instances need to share.

CacheReturn popular data faster

Keep a product page or API result briefly so the system does not query the main database every time.

SessionKeep interaction state

Share login, cart, or multi-step workflow state across multiple application servers.

Rate limitControl request volume

Track how many requests a client has made in a time window and reject excess traffic.

CounterUpdate a number quickly

Maintain views, attempts, inventory signals, or other short-lived counts with atomic increments.

04 · Where is it used?

Redis is valuable when the product needs a shared, low-latency answer and the state has a clear lifetime or recovery plan.

High-traffic readsProduct and content cache

Serve frequently requested data quickly while it is still fresh enough for the product.

Identity flowLogin and session state

Let several application servers recognize the same short-lived user interaction.

Abuse controlRate limits

Protect an API or login endpoint with a per-user, per-IP, or per-key request budget.

Temporary stateCodes and holds

Store a verification code, idempotency key, or checkout hold with an expiration time.

Product signalsCounters

Increment views, attempts, or live activity without making the main database handle every tiny update.

Operating questionWhat happens if it is empty?

Design a fallback, rebuild path, or user-safe failure before treating Redis as critical state.

05 · Example

A flash-sale product page can use Redis in several focused ways, while the durable order remains in the main database.

1. A shopper opens the product page. The application checks Redis for a short-lived product-page cache.

2. When the shopper clicks Buy, the service uses a Redis counter or short-lived reservation key to coordinate the busy moment.

3. The service writes the confirmed order to the primary database. Redis can make the path faster, but it is not the final proof of purchase.

4. An expiration removes abandoned reservation state. A cache miss or Redis outage follows the product's fallback behavior.

PM Perspective

Redis is a product-speed and coordination choice, not a feature by itself.

Ask: how fresh must this value be, can it be rebuilt, what is the expiration rule, and what should the user see during a miss or outage?

Business record = durable database. Fast temporary state = Redis when the speed, lifetime, and recovery behavior are explicit.

The exact architecture depends on the role. A cache miss may read from the database and refill Redis; a rate limit may finish inside Redis; an order still needs a durable commit path.

07 · Do Not Confuse

Redis ≠ Cache

Redis is a technology. A cache is a pattern: keep a reusable copy closer to the caller. Redis can provide a cache, but it can also hold sessions, counters, and other state.

Redis ≠ Primary Database

Redis can persist data, but many product designs treat its contents as rebuildable or temporary. Durable business records need an intentional source of truth.

Redis ≠ Message Queue

A queue coordinates work waiting to be processed. Redis usually answers a read or update quickly; a Redis-based queue is a particular design, not what Redis means by default.

Redis ≠ Session

A session is temporary user state. Redis is one place that can store that state, alongside cookies, databases, or other session stores.

Fast ≠ Free

In-memory access is fast, but memory costs money. Expiration, eviction, capacity, replication, and recovery still need operating decisions.

Counter ≠ Final Ledger

A fast counter can support a live signal or guardrail. It should not replace the durable transaction record when correctness and auditability matter.

09 · What to Remember

Redis is a fast shared data store for state that benefits from low latency and has an explicit lifetime, fallback, or recovery plan.

It commonly supports caches, sessions, rate limits, counters, and temporary state. Choosing Redis means also choosing memory capacity, expiration, eviction, persistence, availability, and what happens when the data is missing.

Core idea: Keep fast, shared, temporary state close to the application; keep durable business truth in the system designed to own it.
