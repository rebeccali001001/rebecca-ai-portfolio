## Potential Missing Concepts

- **backend-as-a-service architecture（BaaS 架构）**：页面说明了后端服务打包方式，但没有进一步解释客户端、平台服务与自定义服务端之间的边界。
- **serverless（无服务器）**：Edge Functions 和托管后端能力出现了，但没有说明开发者是否需要管理服务器。
- **cloud computing（云计算）**：Cloud Firestore、Cloud Storage 和托管环境出现了，但没有定义云资源的基本概念。
- **SQL query（SQL 查询）**：页面提到 SQL-first，但没有展示查询、插入、更新等具体操作。
- **schema（模式／结构）**：数据建模和关系型数据出现了，但没有解释数据库 schema。
- **table / row / column（表／行／列）**：row-level security 出现了，但没有系统说明表、行、列之间的关系。
- **primary key / foreign key（主键／外键）**：关系型概念出现了，但没有介绍记录如何唯一标识和互相连接。
- **NoSQL（非关系型数据库）**：Firestore 的文档模型出现了，但没有把它和 NoSQL 作为更大的类别联系起来。
- **document / collection（文档／集合）**：Cloud Firestore 的 document-oriented 模型出现了，但没有解释文档和集合的结构。
- **CRUD（增删改查）**：平台提供数据库访问能力，但没有明确列出 create、read、update、delete 四类操作。
- **query（查询）**：数据库和 API 出现了，但没有单独解释按条件查找数据的动作。
- **transaction（事务）**：页面没有说明多个数据操作如何保持一致性。
- **consistency（数据一致性）**：实时数据库变化和多服务流程出现了，但没有讨论不同读取结果的一致程度。
- **replication（复制）**：平台和数据库规模出现了，但没有介绍数据副本和同步。
- **availability（可用性）**：托管服务和产品运行被提及，但没有定义服务可用时间或故障影响。
- **latency（延迟）**：实时能力出现了，但没有说明从请求到响应或消息到达需要多久。
- **throughput（吞吐量）**：scale 被提及，但没有说明单位时间内可以处理多少请求或数据。
- **rate limit（速率限制）**：API 和托管平台出现了，但没有介绍请求频率限制。
- **quota（配额）**：平台规模与周边服务出现了，但没有说明资源使用上限。
- **pricing / cost（定价／成本）**：平台选择被讨论，但没有比较托管、存储、请求和流量成本。
- **vendor lock-in（供应商锁定）**：Supabase 的开放工具和 Firebase 的 Google 生态出现了，但没有讨论迁移难度。
- **portability（可迁移性）**：平台选择与开源取向出现了，但没有说明数据和应用能否迁移到其他平台。
- **backup / restore（备份／恢复）**：数据库和文件存储出现了，但没有介绍数据恢复机制。
- **data migration（数据迁移）**：平台替换或模型选择可能需要迁移，但页面没有展开迁移过程。
- **database connection（数据库连接）**：API 与客户端集成出现了，但没有解释应用如何安全建立数据库连接。

## Do Not Confuse Candidates

- **Backend platform vs database**：数据库主要保存数据；后端平台通常还包括认证、文件存储、API、实时能力和其他服务。
- **Data platform vs database platform**：data platform 可能涵盖数据管理和服务的更大范围；database platform 更强调数据库本身及其操作。
- **Backend-as-a-service vs backend**：BaaS 是一种由服务商托管、打包提供后端能力的方式；backend 是更宽泛的后端概念。
- **Auth vs authorization**：Auth 常指 authentication，即确认是谁；authorization 是确认这个人或程序被允许做什么。
- **Authentication vs session**：authentication 是完成身份确认；session 是在一段时间内保持登录身份的状态。
- **Identity provider vs application**：身份提供商负责提供或验证身份；应用仍然负责自己的业务和用户体验。
- **Row-level security vs authentication**：RLS 控制具体数据行能否被访问；authentication 只解决访问者是谁。
- **Storage vs database**：Storage 常用于文件和媒体；database 更适合有结构的数据记录，两者都能保存内容但用途不同。
- **File storage vs media storage**：file storage 可以保存各种文件；media storage 更强调图片、音频、视频等媒体资产。
- **API vs SDK**：API 是软件之间调用的约定；SDK 是帮助开发者使用 API 的工具和代码库。
- **REST vs API**：REST 是设计 API 的一种风格；API 是更大的总称，不是所有 API 都是 REST。
- **Generated API vs handwritten API**：generated API 根据数据或服务定义自动生成；handwritten API 通常由开发者手工编写。
- **Realtime vs messaging**：Realtime 强调变化及时到达或反映；messaging 强调消息的发送和接收，两者常一起使用但重点不同。
- **Realtime Database vs Realtime**：Realtime Database 是 Firebase 的具体数据库产品；Realtime 是更广泛的实时能力概念。
- **Database change vs message**：数据库变化是数据状态发生了改变；消息是用于通知或传递信息的内容。
- **Edge Functions vs server-side logic**：Edge Functions 是一种靠近边缘运行的服务端函数；server-side logic 还包括普通服务器上的后端逻辑。
- **Supabase vs PostgreSQL**：Supabase 是平台；PostgreSQL 是 Supabase 所围绕的关系型数据库。
- **Supabase vs Firebase**：两者都是应用开发／后端平台，但 Supabase 以 PostgreSQL 和关系型模型为中心，Firebase 更常以托管服务、SDK 和文档或实时 JSON 数据模型为中心。
- **PostgreSQL vs SQL**：PostgreSQL 是数据库产品；SQL 是操作关系型数据的语言。
- **Postgres vs PostgreSQL**：Postgres 通常是 PostgreSQL 的简称，不是另一个独立的数据库类别。
- **Cloud Firestore vs Realtime Database**：两者都是 Firebase 数据能力，但 Firestore 面向文档，Realtime Database 更强调实时 JSON 数据。
- **Firestore vs document**：Firestore 是具体产品；document 是它所使用的数据组织单位。
- **Cloud Storage vs Hosting**：Cloud Storage 主要保存文件；Hosting 主要把网站或应用内容提供给访问者。
- **Hosting vs backend platform**：Hosting 是发布和提供网站内容的一项能力；backend platform 是包含多种后端服务的更大组合。
- **SDK-first vs open-source-oriented**：SDK-first 描述开发者接入方式；open-source-oriented 描述平台的工具和生态取向。
- **Google-backed vs Google-owned concept**：Google-backed 表示与 Google 生态有支持或关联，不等于每项具体服务都是相同的产品或功能。
- **Relational vs document-oriented**：关系型模型通过表和关系组织数据；文档模型通过文档或 JSON 结构组织数据。
- **Relational need vs document need**：这是应用需求的选择维度，不是两个具体数据库产品。
- **Application data vs database**：application data 是被应用使用的数据；database 是保存和管理这些数据的系统。
- **Managed service vs open-source software**：托管服务描述谁负责运行维护；开源软件描述软件的源码和开放协作方式，两者可以同时存在。
- **Open-source tooling vs open-source database**：tooling 指工具链；database 指具体的数据存储产品。
- **Developer experience vs user experience**：开发者体验关注开发和维护平台的过程；用户体验关注最终用户使用产品的过程。
- **Event-driven integration vs API request**：事件驱动集成通常由变化自动触发；API request 通常由调用方主动发起。
- **Event-driven vs realtime**：事件驱动描述触发机制；实时描述变化或消息是否及时反映，二者可以组合但不是同义词。
- **Scale vs scalability**：scale 可以表示当前要处理的规模；scalability 更强调系统随规模增长而扩展的能力。
- **Mobile requirement vs mobile product**：mobile requirement 是需求条件；mobile product 是最终面向移动设备的产品。
- **Typical use vs universal winner**：典型用途是适合某类场景；它不意味着某个平台在所有场景都最好。
- **Provider rule vs security rule**：provider rule 是平台或服务商制定的规则；security rule 专门关注访问和安全控制。
- **Platform layer vs product layer**：平台层提供通用能力；产品层把这些能力组合成用户能直接使用的应用。
- **Managed database vs database**：managed database 是由服务商运维的数据库；database 是更宽泛的数据库概念，也可以自建。
- **Service integration vs service capability**：integration 是把多个服务连起来；capability 是单个服务提供的功能。
- **File vs media**：file 是存储单位；media 是图片、音频、视频等内容类别。
- **Web product vs mobile product**：Web product 主要通过 Web 访问；mobile product 主要面向手机或其他移动设备，实际产品可以同时支持两者。
