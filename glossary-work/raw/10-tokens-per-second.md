## Potential Missing Concepts

These are adjacent or implied concepts that would strengthen a later glossary entry but are not fully defined on the source page:

- **Throughput:** broader work-output rate; clarify whether the page uses TPS as a single-request decode rate or a system-level aggregate.
- **Time to First Token (TTFT):** the page names the metric but does not provide a formal abbreviation or measurement boundary beyond the initial wait.
- **Inter-token latency (ITL):** time between successive generated tokens; useful for distinguishing steady token cadence from the aggregate TPS rate.
- **End-to-end latency:** the page names total response time but does not formally break down request, network, queue, setup, generation, and delivery phases.
- **Prefill / prompt processing:** the page mentions context time but does not name the input-processing phase separately from output decoding.
- **Decode phase:** the repeated next-token generation phase is described procedurally but not named as decoding.
- **Input tokens versus output tokens:** the page focuses on output tokens; it does not define the distinction explicitly.
- **Tokenization:** needed to explain why token counts cannot be read as word counts.
- **Output length:** the examples demonstrate that more tokens take longer, but the relationship is not expressed as an explicit equation.
- **Streaming:** the page implies tokens can appear as they are emitted, but does not name streaming output.
- **Batching and concurrency:** relevant to system-level TPS but absent from this single-request explanation.
- **Hardware and model effects:** model size, accelerator, quantization, and runtime can change TPS but are not discussed here.
- **Warm-up and cold-start time:** possible contributors to setup time that are not unpacked.
- **Network transfer time:** network is named as a factor, but upload/download and transport details are not explained.
- **Stopping criteria:** the page does not explain what ends the repeat loop or determines complete output.
- **Maximum output tokens:** a practical control on output length that is not covered.

## Notes

- The source page is intentionally introductory and defines TPS in plain language as the number of output tokens generated in one second.
- The raw inventory preserves repeated semantic coverage: the same concept may appear as a title, lowercase phrase, process label, example phrase, related tag, or comparison heading.
- The source’s clearest operational formula is “generated tokens divided by generation time”; the page does not provide a symbolic equation or specify whether the timing is averaged, instantaneous, streamed, or aggregated.
- The page explicitly scopes TPS to generation after output starts. It separately names time to first token, context time, setup time, network, and total response time as factors that affect the overall wait.
- The two examples provide intentionally different rates and output sizes: 40 TPS for a short answer and 20 TPS for a long report. They illustrate that output length matters in addition to rate.
- The printer analogy maps TPS to pages per minute, while printer startup, document size, and connection stand for additional timing factors.
- The process flow is **Input → Predict → Emit → Repeat → Measure**. It should be retained as a mechanism/workflow sequence for later glossary editing.
- Related concepts shown by the page are **Latency**, **Token**, **KV Cache**, and **Context Window**; the concept chain is **Context → Inference → First token → Tokens per second → Complete output**.
- Video metadata is included because the extraction scope covers the visible video block, but media labels such as “visual explainer,” “video,” and “English captions” are secondary glossary candidates.
- No candidates were deduplicated, normalized, or removed from this raw pass. Editorial selection and canonical-term decisions belong to a later stage.
