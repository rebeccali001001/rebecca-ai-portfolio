## Potential Missing Concepts

- **feedback loop（反馈循环）**：页面展示了 loop 和 feedback，但没有单独定义反馈如何回到后续改进决策。
- **closed loop / closed-loop improvement（闭环／闭环改进）**：页面有循环流程，但没有明确说明“闭环”要求从结果回流到下一轮行动。
- **root cause analysis（根因分析）**：页面要求 investigate traces、feedback、invoices 和 workflow context，但没有展开如何区分根因与表面症状。
- **observability（可观测性）**：monitoring、traces 和 evidence 出现了，但没有说明系统是否能被充分观测和诊断。
- **telemetry（遥测数据）**：页面没有具体定义线上运行时采集的事件、日志、指标和追踪数据。
- **logging（日志记录）**：traces 出现了，但没有说明日志如何记录事件和错误。
- **metrics（指标）**：页面列出业务结果，却没有定义用于持续衡量它们的指标。
- **KPI（关键绩效指标）**：business outcome 出现了，但没有说明哪些结果应作为 KPI 跟踪。
- **SLO / SLA（服务目标／服务等级协议）**：reliability、faster turnaround 和 lower cost 出现了，但没有明确服务目标或承诺。
- **success criteria（成功标准）**：evaluate a change 出现了，但没有说明发布前应满足哪些通过条件。
- **baseline（基线）**：页面没有说明改动前的表现如何作为比较基准。
- **before-and-after comparison（前后对比）**：页面说 evaluate，却没有具体讲改动前后如何比较。
- **A/B testing（A/B 测试）**：代表性发票和评估出现了，但没有说明通过不同版本对照验证。
- **offline evaluation（离线评估）**：页面提到 representative invoices，但没有区分上线前离线测试和线上评估。
- **online evaluation（线上评估）**：production monitoring 出现了，但没有说明线上真实流量中的评估方式。
- **regression testing（回归测试）**：系统修改后可能影响已有能力，但页面没有定义回归测试。
- **test set（测试集）**：代表性数据出现了，但没有介绍独立测试集的组织方式。
- **evaluation dataset（评估数据集）**：页面没有说明用于反复比较版本的固定评估数据集。
- **data drift（数据漂移）**：真实输入可能随时间变化，但页面没有讨论输入分布变化。
- **concept drift（概念漂移）**：业务规则或输入与结果的关系可能变化，但页面没有定义这一现象。
- **distribution shift（分布偏移）**：没有说明生产数据和开发/评估数据不一致的风险。
- **feedback quality（反馈质量）**：feedback 出现了，但没有说明反馈可能不完整、含噪或有偏。
- **label quality（标签质量）**：invoice categories 和 validation appear in context，但没有说明人工答案或分类标签的质量。
- **human feedback（人工反馈）**：页面提到 users 和 review，但没有单独定义人工反馈的采集和利用。
- **error budget（错误预算）**：reliability improvement 没有对应的可接受失败范围概念。
- **incident（事故／事件）**：problem、failure handling 和 monitoring 出现了，但没有定义生产事故。
- **incident response（事故响应）**：页面没有说明发现严重问题后谁负责、如何升级和处置。
- **rollback（回滚）**：release 和 redeploy 出现了，但没有说明失败版本如何恢复到旧版本。
- **canary release（灰度发布）**：deploy again 出现了，但没有介绍逐步放量验证。
- **blue-green deployment（蓝绿部署）**：页面没有讨论两套生产环境之间的切换策略。
- **feature flag（功能开关）**：没有说明如何逐步打开或关闭某项改进。
- **versioning（版本管理）**：prompt、workflow、model 和 controls 可能变化，但页面没有定义版本记录。
- **experiment tracking（实验跟踪）**：hypothesis 和 evaluate 出现了，但没有定义如何记录实验过程和结论。
- **change log（变更日志）**：页面没有说明如何记录每轮改了什么以及为什么改。
- **champion/challenger（主版本／挑战版本）**：页面没有介绍保留当前版本并比较候选版本的方法。
- **guardrail（护栏）**：controls、validation、permissions 出现了，但没有用 guardrail 统一描述约束机制。
- **human-in-the-loop（人在回路中）**：approval 和 review 相关，但没有展开人工在关键步骤中的职责。
- **human approval gate（人工审批关口）**：approval 出现了，但没有说明在哪些动作前必须暂停等待人批准。
- **risk-based approval（基于风险的审批）**：不同任务可能需要不同审批强度，页面没有定义这种分级。
- **governance（治理）**：controls 和 permissions 出现了，但没有讨论责任、政策和审计治理。

## Do Not Confuse Candidates

- **Continuous Improvement vs Fine-tuning**：持续改进可以修改 prompt、RAG、tools、workflow、UI、controls 或 model；fine-tuning 只是改变模型参数的一种具体方法。
- **Continuous Improvement vs Monitoring**：monitoring 负责观察并产生 evidence；continuous improvement 负责根据学到的内容采取 change。
- **Monitoring vs Evaluation**：monitoring 关注线上持续发生什么；evaluation 通常是对系统或候选改动进行有目的的测试。
- **Evaluation vs Monitoring**：评估不是简单地看运行日志，而是用测试或比较判断是否达到标准。
- **Deployment vs Release**：deployment 强调让系统进入运行环境；release 强调把某个版本或改动提供给用户。
- **Deploy again vs Constantly changing everything**：再次部署应建立在验证后的 focused change 上，不等于每次都全面改动。
- **Evidence vs Signal**：signal 是提示需要关注的观察；evidence 是支持判断或决策的更完整信息。
- **Signal vs Problem**：signal 可能只是异常线索，不一定已经证明存在根因问题。
- **Hypothesis vs Conclusion**：hypothesis 是待验证的猜想，不是调查后已经确认的结论。
- **Change vs Improvement**：change 只是发生了修改；improvement 还要求结果朝更有用、更可靠或更有效的方向变好。
- **Prompt vs Prompt Design**：prompt 是具体指令；Prompt Design 是设计和改进指令的方法。
- **Prompt vs Model**：prompt 是输入和指导；model 是处理输入并产生结果的机制。
- **RAG vs Fine-tuning**：RAG 在任务时提供检索到的外部资料；fine-tuning 通过额外训练改变模型参数。
- **RAG vs Retrieval**：retrieval 是找资料的动作或能力；RAG 是把检索结果用于生成的完整模式。
- **Tools vs Workflow**：tool 是可调用的外部能力；workflow 是完成任务的完整步骤安排。
- **Tool vs Integration**：tool 是系统能使用的能力；integration 是把系统和外部服务连接起来的机制。
- **Workflow Improvement vs Model Upgrade**：有时应改业务步骤或交接方式，而不是只换模型。
- **UI vs User Experience**：UI 是界面本身；user experience 是用户对整个使用过程的感受。
- **Model vs AI System**：model 只是 AI system 的一个组件；系统还包括数据、提示、工具、流程和控制。
- **Model Upgrade Only vs Whole-System Improvement**：模型升级只是一个选项，页面明确强调提示、数据、workflow、UI 和 controls 可能更重要。
- **Fine-tuning vs Model Upgrade**：fine-tuning 是对模型做额外训练；model upgrade 通常是换用另一个模型版本。
- **Model Parameters vs Controls**：parameters 是模型内部学到的数值；controls 是外部规则、验证、权限和审批机制。
- **Validation vs Approval**：validation 可以由规则或程序执行；approval 通常是有权限的人或机制做出的放行决定。
- **Permissions vs Approval**：permissions 决定谁有权做事；approval 决定某个具体动作是否被允许继续。
- **Validation Rule vs Policy**：validation rule 检查某个值或结果；policy 是更广泛的组织规定或处理原则。
- **AI Invoice Assistant vs Invoice**：AI Invoice Assistant 是处理发票的系统；invoice 是被处理的业务单据。
- **Tax-category Suggestion vs User Decision**：AI 建议不是最终决定，用户可以 override。
- **Override vs Feedback**：override 是一次具体的替换操作；feedback 可以包括意见、评分、纠正或其他信号。
- **Trace vs Feedback**：trace 记录系统运行经过；feedback 表示用户或评审对结果的反应。
- **Investigate vs Evaluate**：investigate 主要为了理解问题原因；evaluate 主要为了判断结果或改动是否达到标准。
- **Representative Invoice vs Every Invoice**：representative invoice 用于代表性测试，不等于覆盖所有真实发票。
- **Verified Change vs Proposed Change**：proposed change 还只是计划；verified change 已经经过测试或检查。
- **Business Outcome vs System Metric**：业务结果关心人工量、错误、时间、采用率、成本和可靠性；系统指标可能只是其中的技术观测。
- **Fewer Errors vs Zero Errors**：更少错误表示错误率下降，不表示系统永远不会出错。
- **Better Reliability vs Perfect Reliability**：可靠性变好不等于绝对不会失败。
- **Better Adoption vs Forced Usage**：采用率高应反映用户成功使用和认可，不只是被要求打开系统。
- **Lower Cost vs Lower Model Price**：业务成本下降可能来自更少人工、错误或返工，不只是模型单价降低。
- **Less Manual Work vs No Human Work**：人工工作减少不等于所有环节都不需要人。
- **Real-world Evidence vs Synthetic Test Data**：真实证据来自生产使用；合成测试数据可以辅助评估，但不完全等同。
- **Production Monitoring vs Pre-release Evaluation**：线上监控发生在真实运行中；发布前评估发生在上线前或受控测试环境。
- **Improvement Loop vs One-time Launch**：循环意味着上线后仍持续观察和改进；一次性上线把发布错误地当作终点。
- **Continuous Improvement vs Constant Change**：持续改进需要 evidence、focused change 和 evaluation，不是无目标地不停改。
- **Independent Explainer vs Core System Capability**：视频或视觉讲解是呈现方式，不是 AI 系统改进机制本身。
- **Not Available Yet vs Missing Core Concept**：视频暂不可用是页面资源状态，不代表 continuous improvement 的核心定义缺失。

## Notes

- 本文件是 Module 12 · Enterprise AI Deployment 中 `continuous-improvement.html` 的 raw glossary 收集稿，目标是最大化保留正文候选，不做最终去重、归并或删减。
- 页面核心定义是：continuous improvement 是利用 real-world evidence，使 AI system 随时间变得更 useful、reliable、effective 的 ongoing process；目标是改进 whole system，而不只是 model。
- 页面明确给出的 Production AI 主循环是：DEPLOY → MONITOR → LEARN → IDENTIFY PROBLEM → IMPROVE → EVALUATE → DEPLOY AGAIN。
- 页面又用更短的 Improvement Loop 表达同一主线：SIGNAL → HYPOTHESIS → CHANGE → EVALUATE → DEPLOY → MONITOR ↺。
- 页面要求“Use evidence. Do not change the system blindly.” 因此 evidence-based change、focused change、evaluated change 和 blind change 都应保留为重要候选及边界概念。
- 页面列出的可改进层包括 PROMPT、RAG、TOOLS、WORKFLOW、UI、MODEL 和 CONTROLS；对应的正文解释分别涉及 instructions、retrieval、actions/integrations、process design、user experience、different model/fine-tuning、validation/permissions/approval。

- 页面把 Continuous Improvement 与 Fine-tuning 对比：前者改进 entire AI system，后者是一个 specific model-adaptation technique，并且 changes model parameters。
- 页面把 Monitoring 与 Continuous Improvement 对比：前者 observes what is happening → evidence，后者 acts on what was learned → change。
- 页面把改进与业务结果连接为：SYSTEM IMPROVEMENT → WORKFLOW IMPROVEMENT → BUSINESS OUTCOME；正文列出的 outcomes 是 less manual work、fewer errors、faster turnaround、better adoption、lower cost、better reliability。
