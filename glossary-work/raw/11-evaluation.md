## Potential Missing Concepts

The following are high-value glossary concepts suggested by the page’s structure or module context but not explicitly defined in `evaluation.html`. They are retained as candidates for later coverage review and are not presented as page-defined facts.

- **benchmark / benchmark test**：标准化测试，用来比较系统表现；页面只说 metrics、test data 和 comparison。
- **evaluation dataset / test set**：专门用于评测的数据集合；页面说 test data，但没有解释数据集划分。
- **training set / validation set / holdout set**：训练、调参和最终检验之间的数据边界；正文没有展开。
- **golden dataset / golden answers**：带有可信标准答案的评测样本；正文没有说明 ground truth。
- **ground truth**：用于判断输出正确与否的参考事实或标准答案。
- **annotation / annotator**：为案例或输出添加 labels 的标注过程和标注人员。
- **rubric**：把质量、正确性、帮助性等转成可执行评分规则的量规。
- **automated evaluation**：由规则、程序或模型自动评分的评测。
- **human evaluation / human-in-the-loop evaluation**：由人工检查或持续参与的评测。
- **LLM-as-a-judge**：让一个语言模型按标准评价另一个模型的输出。
- **offline evaluation**：在离线数据上发布前进行的评测。
- **online evaluation**：真实流量或线上使用中的评测。
- **A/B test**：把不同系统版本随机分流比较的线上实验。
- **canary release**：先向少量用户发布以收集风险证据。
- **regression test**：改动后确认原本通过的行为没有退化。
- **error analysis**：按错误类型、原因和场景分析失败结果。
- **slice / subgroup analysis**：按语言、用户群、输入类型等子群体切分比较。
- **accuracy**：预测或答案正确的比例。
- **precision / recall / F1**：分类或检索任务常用的精确率、召回率和综合指标。
- **exact match**：输出是否与标准答案完全匹配。
- **BLEU / ROUGE**：文本生成的词面重叠类指标；页面没有给出具体指标。
- **relevance**：回答是否与用户问题相关。
- **faithfulness / groundedness**：回答是否忠实于提供的依据，而不是凭空生成。
- **factuality**：内容是否符合可验证事实。
- **toxicity**：输出是否包含侮辱、仇恨或有害表达。
- **bias / fairness**：不同群体之间是否存在系统性不公平差异。
- **privacy**：系统是否泄露或不当使用敏感信息。
- **security evaluation**：对攻击、越权、操纵等安全风险的评测。
- **adversarial testing / red teaming**：主动构造攻击性或极端输入来寻找风险。
- **prompt injection**：恶意输入试图改变模型规则或诱导其越权。
- **robustness testing**：在噪声、歧义、分布变化或困难输入下测试稳健性。
- **distribution shift / data drift / concept drift**：线上输入或任务规律与评测数据发生变化。
- **monitoring**：上线后持续观察系统信号、指标和风险。
- **observability**：让系统行为、失败和运行状态可被记录与诊断。
- **re-evaluation**：发生模型、数据、提示词或环境变化后重新评测。
- **calibration**：模型置信度与真实正确概率是否匹配。
- **confidence / uncertainty**：系统对答案或判断的信心和不确定程度。
- **pass rate / failure rate**：通过案例和失败案例的比例。
- **task completion rate**：任务最终完成的比例。
- **user satisfaction / CSAT**：用户对结果或体验的满意程度。
- **latency breakdown**：把总延迟拆成检索、推理、网络等组成部分。
- **throughput**：单位时间处理的请求、样本或 token 数量。
- **time to first token (TTFT)**：从请求发出到首个 token 返回的时间。
- **p50 / p95 / p99 latency**：中位数和高分位延迟，用来观察长尾等待时间。
- **cost per request / cost per task**：每次请求或每个任务的运行成本。
- **sample size**：评测案例数量；样本太少可能让结论不稳定。
- **confidence interval**：指标估计的不确定范围。
- **statistical significance**：差异是否可能只是随机波动。
- **reproducibility**：相同条件下能否重复得到相近评测结果。
- **threshold**：决定通过、拒绝或触发人工处理的分数界线。
- **release gate / readiness gate**：把质量、安全和可靠性证据汇总成发布闸门。
- **deployment readiness**：是否达到真实部署所需的证据和控制要求。
- **rollback**：上线后发现问题时恢复到旧版本。
- **fallback**：系统失败时转向较安全或较简单的备用路径。
- **incident response**：上线风险事件发生后的处理流程。
- **SLA / SLO**：服务可用性、延迟等运营承诺和目标。
- **failure mode**：系统可能失败的具体方式；相关链接出现，但本页没有展开定义。
- **failure handling**：发生失败时系统应该采取的安全响应；属于父模块相关概念。
- **guardrails**：限制危险行为、工具调用或输出的安全控制。
- **permissions**：控制系统可以访问什么、执行什么动作的权限边界。
- **approval**：高风险动作执行前需要人工批准的控制点。
- **human handoff**：将无法安全自动处理的任务交给人工。

## Do Not Confuse Candidates

- **Evaluation vs Functional Test**：Evaluation 可跨多个维度衡量表现；functional test 主要检查一个定义好的功能是否工作。
- **Evaluation vs User Feedback**：Evaluation 使用计划好的测量方法；user feedback 是用户体验的一种证据来源。
- **Evaluation vs Benchmark**：Evaluation 问“我们的系统是否满足要求”；benchmark 更常问“在标准测试上表现如何”。
- **Evaluation vs Testing**：Testing 常聚焦预设行为是否通过；evaluation 可以同时纳入质量、安全、成本、延迟、可靠性和用户结果。
- **Evaluation vs Monitoring**：Evaluation 通常是有计划的比较与判断；monitoring 是运行中持续观察信号和变化。
- **Evaluation vs One Number**：完整评测可以包含多个维度；单一分数可能隐藏安全、成本或可靠性的权衡。
- **Metric vs Label**：Metric 是衡量规则或量化指标；label 是附着在案例或输出上的判断/标注。
- **Metric vs Score**：Metric 定义如何测量；score 是应用 metric 后得到的数值结果。
- **Quality vs Correctness**：Quality 是更宽的整体质量；correctness 主要回答内容或任务结果是否正确。
- **Correctness vs Helpfulness**：答案可能事实正确但对用户没帮助，也可能看起来有帮助但事实错误。
- **Latency vs Throughput**：Latency 是一次请求等多久；throughput 是单位时间能处理多少工作。
- **Cost vs Quality**：降低成本不等于提高质量；二者可能需要明确权衡。
- **Robustness vs Reliability**：Robustness 强调面对变化、困难或扰动仍能工作；reliability 更宽泛地强调持续可依赖。
- **Safety vs Security**：Safety 关注伤害和不安全行为；security 更关注攻击、越权、操纵和数据保护。
- **Human Review vs User Feedback**：human review 是按评测方法检查输出；user feedback 是真实用户提供的体验反馈。
- **Human Review vs Human Handoff**：review 是检查或评分；handoff 是把处理责任交给人工。
- **Test Data vs Production Data**：test data 是评测时选定的数据；production data 来自真实运行场景，二者用途和风险不同。
- **Test Case vs Task**：task 是要完成的工作；test case 是用来检查该任务的一个具体输入或场景。
- **Test Case vs Example**：example 可以只是说明概念；test case 被有意纳入评测并需要判断结果。
- **Evidence vs Decision**：evidence 支持判断；decision 是基于证据采取的行动。
- **Release Decision vs Release**：release decision 是是否发布的选择；release 是实际让系统可用的事件。
- **Release vs Deployment Readiness**：readiness 表示证据是否足够；release/deployment 是实际上线动作。
- **Deployment vs Adoption**：deployment 是系统被部署；adoption 是用户是否真正采用和使用。
- **Grounding vs Correctness**：grounding 关注回答是否有依据；有依据不必然代表事实完全正确。
- **Grounding vs Retrieval**：grounding 是让回答受依据约束；retrieval 是寻找并取回信息的机制。
- **Quality Score vs Overall Quality**：质量分数只是测量结果；一个分数不一定完整代表整体质量。
- **Fluency vs Correctness**：语言流畅只说明表达自然，不能证明内容正确或安全。
- **Useful Behavior vs Safe Behavior**：有用行为帮助完成任务；安全行为还必须避免不可接受的风险。
- **Common Cases vs Difficult Cases**：常见案例代表典型使用；困难案例专门暴露边界和弱点。
- **Difficult Cases vs Risky Cases**：困难是处理难度高；风险是出错后果严重，二者可能重叠但不相同。
- **Labels vs Human Review**：labels 是结果上的标注；human review 是产生判断或标注的过程。
- **Improvement vs Redesign**：improvement 可以是局部修正；redesign 可能重新设计整个流程或系统。
- **Failure Mode vs Failure Handling**：failure mode 是“怎么失败”；failure handling 是“失败后怎么办”。本页只通过 related link 提及 failure modes。
- **Evaluation vs Road-Safety Check**：道路安全检查是帮助理解评测的类比，不是 AI 评测的正式方法名。
- **AI System vs Model**：AI system 可包含模型、提示、工具、数据和流程；model 只是其中一个组件。
- **User Feedback vs User Outcomes**：feedback 是用户表达的意见；outcomes 是用户实际获得的结果。
- **Metric vs Real Decision**：metric 提供测量信息；real decision 还要结合目标、风险和约束。
- **Reliability vs Guarantee**：reliability 是基于证据的可依赖程度；不表示系统绝不会出错。
- **Safety Control vs Safety Guarantee**：控制措施可以降低风险；不能自动保证完美安全。
- **One Number vs Multi-dimensional Evaluation**：单一数字便于摘要；多维评测才能暴露不同方面的取舍。
