## Do Not Confuse Candidates

- **Local AI vs Cloud AI**：两者主要区别是推理发生在哪里，以及谁管理计算基础设施；不是简单的“好模型 vs 坏模型”。
- **Local AI vs local app**：本地 AI 说的是模型推理位置；本地 app 说的是应用运行位置。本地应用仍可能调用在线服务。
- **Local AI vs offline**：模型在本地运行不保证整个系统无需网络；“local”与“offline”是两个不同维度。
- **Local AI vs free**：本地推理可能避免某些按 token 的 API 费用，但硬件、电力、配置和维护仍然有成本。
- **Cloud AI vs internet**：云端 AI 通常依赖网络，但 internet 是连接条件，cloud AI 是模型运行方式。
- **Cloud provider vs cloud model**：provider 是提供和管理基础设施的组织；model 是在该基础设施上运行的计算模型。
- **Cloud provider vs cloud hardware**：provider 是服务提供者；cloud hardware 是提供者控制的物理或虚拟计算资源。
- **Remote infrastructure vs cloud provider**：infrastructure 是资源环境；provider 是管理或提供这些资源的组织。
- **Local hardware vs local model**：hardware 是实体设备；model 是在设备上运行的软件/参数集合。
- **Runtime vs model**：runtime 负责执行模型；model 负责根据输入产生推理结果。
- **Local runtime vs local model**：运行时是执行环境，模型是被执行的对象，二者不是同一个组件。
- **Model inference vs model training**：页面讨论的是使用模型产生结果的推理，不是训练模型的过程。
- **Inference vs output**：inference 是运行过程；output/result 是运行产生的内容。
- **Execution environment vs execution path**：environment 是在哪里运行；path 是请求依次经过哪些组件。
- **API vs cloud AI**：API 是访问接口；cloud AI 是模型在远程基础设施运行的部署方式。
- **API consumption vs API fee**：consumption 是使用行为；fee 是该使用行为可能产生的费用。
- **Usage pricing vs total cost**：usage pricing 只是按调用量收费的方式；total cost 还可能包含硬件、电力、维护和配置。
- **Usage-based pricing vs fixed cost**：usage-based 随使用量变化；fixed cost 不直接随每次请求变化。
- **Hardware limits vs provider limits**：前者来自本地设备，后者来自云服务商的能力、配额或政策。
- **Model size vs model capability**：模型大小影响资源需求，但大小本身不等于任务能力或质量。
- **Compute vs memory**：compute 是处理能力；memory 是运行时存放数据和模型所需的容量。
- **Scaling vs scale**：scaling 是扩展能力或过程；scale 是需要处理的需求规模。
- **Scale vs latency**：scale 关注能处理多少需求；latency 关注单次请求多快返回。
- **Network dependency vs provider dependency**：network dependency 是依赖连接；provider dependency 是依赖服务商的服务、政策和可用性。
- **Offline operation vs online service**：offline 不用网络；online service 依赖网络访问远程能力。
- **Data control vs data ownership**：页面讨论的是谁控制处理路径，不等于法律意义上的数据所有权。
- **Privacy vs data governance**：privacy 关注信息暴露和使用；governance 还包括组织规则、责任和流程。
- **Privacy vs security**：隐私关注数据应由谁、以何种方式处理；安全还包括防攻击、访问控制和系统防护。
- **Data can remain local vs data must remain local**：页面说可以留在本地，不代表所有部署或所有数据都必须留在本地。
- **Local control vs predictable local infrastructure**：local control 是控制权；predictable infrastructure 是可预期性，二者相关但不同。
- **Managed infrastructure vs no infrastructure**：云端是服务商管理基础设施，不是没有基础设施。
- **Managed infrastructure vs fully automatic**：托管减少用户维护工作，但仍可能存在 provider limits、治理和运维责任。
- **Setup effort vs operational complexity**：setup 是初始搭建工作；operational complexity 包括长期运行和维护。
- **Maintenance vs setup**：setup 是开始前的准备；maintenance 是持续的维护。
- **Provider-dependent vs provider-controlled**：provider-dependent 表示依赖服务商；不必然表示用户完全没有任何控制。
- **Hybrid AI vs choosing both at once**：混合 AI 不是每个请求同时调用本地和云端，而是可以按任务组合或分流。
- **Small private tasks vs all private tasks**：页面只给出适合本地的示例，不表示所有私密任务都一定适合本地。
- **Complex large-model tasks vs always cloud**：复杂大模型任务可能适合云端，但页面没有说云端对所有复杂任务都是唯一选择。
- **Task routing vs model routing**：task routing 选择运行环境或处理路径；model routing 选择具体模型，二者可能同时发生。
- **Fallback vs primary route**：fallback 是主路径不可用或不合适时的后备路径，不是默认路径。
- **Latency vs speed**：latency 是可测时间延迟；speed 是更宽泛的响应快慢描述。
- **Cost vs price**：price 是服务商标价或收费方式；cost 还包括设备、电力、维护和人工等总投入。
- **Usage cost vs electricity**：usage cost 可指云端调用费用；electricity 是本地硬件消耗的电力成本。
- **Provider limits vs model size limited**：前者是服务商总体限制；后者是模型大小受到设备或 provider 能力边界限制。
- **Internet required: usually vs always**：页面说云端通常需要网络，并没有说任何云端场景绝对无例外。
- **Internet required: maybe vs never**：页面说本地可能需要网络，并没有说本地永远不需要网络。
- **Typical patterns vs absolute rules**：表格是典型模式，不应当被理解为适用于所有架构和供应商的绝对规则。
- **Same user task vs same result quality**：同一个“总结文档”任务不保证本地和云端结果质量完全相同。
- **Same goal vs same execution**：目标可以相同，但执行环境、模型、网络和管理责任可能不同。
- **Document / request vs result**：document/request 是输入；result 是处理后的输出。
- **Local execution chain vs cloud execution chain**：两条链路都能完成任务，但组件顺序和数据经过的位置不同。
- **Result vs final answer**：页面使用 result 作为返回结果；它不一定意味着任何复杂的后处理或最终产品答案。
- **Model capability vs model size**：更大的模型可能带来更强能力，但正文没有声称二者必然正相关。
- **Operational complexity vs computational complexity**：operational complexity 是人和组织运行系统的难度，不是算法计算复杂度。
- **Hardware ownership vs data control**：拥有硬件可能加强本地控制，但硬件所有权不自动解决全部数据治理问题。
- **Cloud provider vs data controller**：服务商提供基础设施，但页面没有定义法律上的数据控制者角色。
- **API path vs model location**：请求通过 API 不代表 API 自己是模型；API 只是访问路径。
- **Offline vs local-only**：local-only 关注模型处理位置；offline 关注有没有网络，二者可以同时成立，也可以分开成立。
- **Cloud-only vs provider-managed**：provider-managed 说明谁管理；cloud-only 还说明相关处理没有本地模型参与。
- **Hybrid AI vs multi-agent system**：hybrid AI 组合的是本地与云端执行环境；multi-agent system 组合的是多个 agent，页面没有讨论后者。
- **Local model vs open-source model**：本地模型不必然开源；页面没有讨论模型许可或权重是否开放。
- **Cloud model vs closed model**：云端模型不必然闭源；页面没有把部署位置等同于许可模式。
- **Data processing location vs data storage location**：页面主要讨论推理处理在哪里运行，不等于数据长期存储在哪里。
- **Privacy / governance vs compliance**：页面提到治理考量，但没有给出具体法规或合规认证。
- **Provider limits vs API rate limit**：provider limits 是更宽泛的服务商限制；rate limit 只是其中可能的一类，正文没有具体命名。
- **Scaling vs autoscaling**：页面说 scaling，但没有声称一定由系统自动扩展。
- **Latency vs throughput**：latency 是单次响应时间；throughput 是单位时间可处理多少工作，后者是扩展候选而非正文指标。
- **Cost vs cost predictability**：cost 是花费多少；cost predictability 是费用是否容易预估，正文没有正式定义后者。
- **Maintenance vs monitoring**：maintenance 是修复和更新；monitoring 是观察运行状态，正文只直接出现 maintenance。
- **Video asset vs source evidence**：视频区是页面媒体占位信息，不是 Local/Cloud 结论的证据。
- **Independent explainer vs verified explainer**：页面标记 independent explainer，但并没有提供可验证的视频资产。
- **Page navigation vs technical mechanism**：Visual、Example、Trade-offs、Remember this 等是页面结构词，不应误当成模型机制。
