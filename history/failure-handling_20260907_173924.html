04 · Prompting & System Design

Failure handling makes “I can’t” a safe product behavior.

AI systems fail in different ways: a transient timeout, missing evidence, invalid fields, unsafe intent, or a tool that should not be called. Good design classifies the failure and chooses a bounded next action.

Topic Detail

A failure path should detect the signal, preserve useful context, and select a response: retry, repair, ask, abstain, or escalate. Make each path observable so the team can learn whether the issue is data, prompt, model, integration, or policy.

DetectWhat signal says this failed?
ClassifyTransient, invalid, unsafe, or unknown?
RecoverWhat is the smallest safe next step?

Why it matters

A polished answer is not the same as a successful workflow. Explicit failure behavior prevents silent corruption, duplicate side effects, and confident invention when the system lacks evidence.

Retry only when the operation is safe to repeat or protected by an idempotency key.

Sample

A pricing assistant cannot retrieve the current policy:

Signal: policy lookup timed out
Class: transient integration failure
Action: retry once with a short backoff
If still missing: do not invent an exception
Return: “I can’t verify the current policy. I’ve routed this to an operator.”

The user gets an honest status and a path forward. The trace records the failure class, retry count, and handoff so the team can fix the right layer.

Easy Analogy

Failure handling is like a road detour sign.

When the main road is closed, a good sign names the problem, points to a safe alternate route, and does not pretend the blocked road is open. Different closures need different detours.
