MODULE 06 · AUTHENTICATION & SECURITY

CSRF

Cross-site request forgery is an attack that tricks a browser into sending an unwanted state-changing request while the user is already signed in.

01 · What is it?

CSRF is a web attack in which an attacker causes a victim's browser to send a request to a trusted site without the victim intentionally taking that action.

The browser may automatically include the victim's session cookie, so the server can mistake the forged request for a real one.

02 · Think of it like...

Think of CSRF like someone hiding a signed form inside an envelope that you unknowingly mail to your bank.

The bank sees your valid signature and processes the form, even though you did not mean to request the transfer.

A CSRF defense adds a second proof that the request came from the real site and the real action.

03 · What does it do?

CSRF defenses help the server distinguish an intentional request from a cross-site request made by a browser.

Prove Origin

Check that a request came from an allowed site or origin.

Require a Token

Match a secret, unpredictable value supplied by the application.

Protect State Changes

Defend actions such as password changes, transfers, and updates.

Reject Suspicious Requests

Stop requests that fail the required validation checks.

04 · Where is it used?

CSRF protection matters when a browser uses ambient credentials, especially cookies, for authenticated requests.

Account Settings

Changing an email address, password, or profile setting.

Payments

Submitting a purchase, transfer, or billing action.

Administration

Creating users, changing roles, or deleting records.

Cookie-Based Sessions

Any state-changing endpoint that trusts a browser session cookie.

05 · Example

<form action="https://bank.example/transfer" method="POST">
  <input name="amount" value="1000">
  <input name="to" value="attacker">
</form>

If the victim is signed in to the bank, a malicious page may cause the browser to submit a request to the bank. The bank should require a valid CSRF token or equivalent protection before accepting the transfer.

The dangerous part is the combination of an unwanted cross-site action and credentials that the browser sends automatically.

06 · How it connects

User→Browser→Request + Cookie→CSRF Check→Server Action

The browser carries the session credential, while the server verifies a CSRF token, origin, or an appropriate cookie policy before changing state.

07 · Do Not Confuse

CSRF

Tricks a browser into sending an authenticated request that the user did not intend.

XSS

Injects or executes untrusted script in a trusted page or application context.

CORS

Controls whether browser scripts may read cross-origin responses; it is not a general CSRF defense.

CSRF is about unwanted actions. XSS is about script execution. CORS is about browser read access across origins.

09 · What to Remember

CSRF abuses credentials that a browser sends automatically to make a trusted site accept an unwanted action.

Protect state-changing requests with a suitable CSRF token, origin check, SameSite cookie policy, or another design that matches the authentication model.

Core Flow:
Browser Request + Ambient Credential → CSRF Validation → Allow or Reject State Change
