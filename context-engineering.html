What Is Context Engineering?

Context engineering is the process of deciding what information and instructions should be available to a model for a specific task.

It is broader than writing a prompt.

Think of it like...

Preparing a briefing folder before someone makes a decision.

Person → Model

Briefing folder → Context

Choosing relevant documents → Context Engineering

The goal is not to hand over every document. It is to assemble relevant, current, well-organized material.

This analogy is for understanding only. Model context is structured information supplied during inference.

Prompt Design vs Context Engineering

Prompt Design

How should I write the instruction?

Context Engineering

What full information environment should the model receive?

Prompt: “Check this invoice.”

Full context: System Rules + Invoice + Policy + Tool Results + History + Output Schema

The prompt is one part of the context.

One Real Example

“Can customer 123 receive a refund?”

Context Engineering selects

  • System Rules
  • User Request — Customer 123
  • Retrieved Policy
  • Tool Result — order status
  • State — current case status
→

Model

Answer / action proposal

DO NOT INCLUDE

irrelevant conversation · unrelated documents · unnecessary sensitive information

Context Engineering is not about adding more information. It is about selecting the right information.

What It Is NOT

Longer Prompt

Longer does not automatically mean better.

More Context

Relevant context matters more than volume.

RAG

RAG is one method for supplying external information into context.

Memory

Stored information is not automatically visible to the current run.
